# RAVEN Mesh Wire-Protocol v2 — signing inputs (DRAFT)

> **Status: draft, not deployed.** No port emits or verifies v2 yet.
> `docs/MESH_PROTOCOL.md` (v1) and `shared-vectors/v1/` remain the contract.
> This is the design doc that `shared-vectors/VERSIONING.md` requires before a
> wire-level fix. Its vectors live in `shared-vectors/v2/` (generated by
> `shared-vectors/generate_v1.py`) and may still change until v2 is adopted;
> after that they are frozen under the same rules as `v1/`.

## 1. Scope

v2 changes **only what is signed**, to fix two v1 flaws:

- **MESH_PROTOCOL.md §I.13 (security).** The v1 pipe forms (Rules 1, 2, 4,
  5) join fields with a bare `|`, so different envelopes can share signing
  bytes. For example, a relay can strip a DM's geo-fence and keep its
  signature valid.
- **MESH_PROTOCOL.md §I.14 (interop).** Rule 3's "sorted keys" JSON has no
  cross-language canonical spelling for numbers, escapes or key order.

Envelope JSON schemas, field sets, transport, encryption and routing are
unchanged from v1. Version signalling is out of scope for this draft. The
existing hook is `EncryptedMeshPayload.v` (MESH_PROTOCOL.md §J), and the rest
waits on the handshake version negotiation that §J lists as a future
addition. Whatever the signalling, §2.1 makes it impossible for a v1 signature
to verify as v2 or the reverse.

## 2. Pipe-form records: DM, Post, ACK, Stop

### 2.1 Signing input

```
sigInput = 0xFF || "RVMESH2" || kind || u16be(n) || field_1 || … || field_n
field_i  = u32be(byte length of utf8(f_i)) || utf8(f_i)
```

- `0xFF || "RVMESH2"` is 8 bytes, `ff52564d45534832`. `0xFF` never occurs in
  UTF-8, and every v1 signing input is UTF-8, so no v2 input equals any v1
  input.
- `kind` is 1 byte: `0x01` DM (v1 Rule 1), `0x02` Post (Rule 2), `0x03`
  feature frame (§3), `0x04` ACK (Rule 4), `0x05` Stop (Rule 5).
- The field list `f_1 … f_n` is **exactly the v1 list for that rule**: same
  order, same string forms (decimal numbers, `"true"`/`"false"`, a missing
  optional as `""`), and the leading `"POST"`/`"STOP"` literals kept. Ports
  reuse their v1 field extraction and change only the framing.
- A DM has `n = 20`, or `n = 23` when a geo-fence is present. A Post has
  `n = 9`, an ACK `n = 5`, a Stop `n = 3`.
- Fields are carried **verbatim**. `|`, `\` and any other character need no
  escaping, and the v1 rule that forbids `|` inside signed fields
  (MESH_PROTOCOL.md §D) does not apply to v2.

Every field is length-prefixed and the count is explicit, so the field list can
be recovered from `sigInput` in exactly one way. Two envelopes whose signed
field lists differ, including a 20-field and a 23-field DM, always have
different signing inputs. As in v1, an absent optional and an empty string sign
the same way, so receivers MUST treat them as equal.

### 2.2 Verification

A verifier rebuilds `sigInput` from the received envelope's fields, exactly as
the signer did, and checks the Ed25519 signature over it. It never splits or
parses a received byte string. Signer keys and which envelope fields are
signed are unchanged from v1.

### 2.3 ACK relay dedup key

```
relayKey = "ack2:" || lowercase-hex( SHA-256( u16be(4) || field(originalMessageId) || field(senderId) || field(recipientId) || field(status) ) )
```

`field(·)` is the §2.1 length-prefixed field. The key is computed only for an
ACK whose signature verified.

## 3. Feature frames (`MeshMessageFrame`, v1 Rule 3)

```
sigInput = 0xFF || "RVMESH2" || 0x03 || utf8( JCS( frame without keys "s" and "spk" ) )
```

`JCS` is RFC 8785 (JSON Canonicalization Scheme):

- Object keys are sorted by their UTF-16 code units, recursively. This is not
  code-point order: U+1F600 sorts before U+E000.
- No insignificant whitespace.
- Strings use minimal escaping: only `"`, `\` and U+0000–U+001F are escaped
  (as `\b \t \n \f \r`, else `\u00xx` with lowercase hex). `/` and non-ASCII
  characters are emitted literally.
- Numbers use ECMAScript `Number.prototype.toString` on the IEEE-754 double:
  `1.0` → `1`, `-0` → `0`, `1e21` → `1e+21`, `1e-7` → `1e-7`,
  `0.000001` → `0.000001`.

Frames MUST be I-JSON (RFC 7493): valid Unicode, no duplicate keys, and
integers only within ±(2⁵³−1). A frame that is not I-JSON cannot be signed or
verified. Floats are fine: JCS gives each double exactly one spelling.
Apple ports get the JCS bytes from a JCS implementation, not from
`JSONSerialization`.

## 4. Vectors

`shared-vectors/v2/canonicalization/` mirrors the v1 paths and reuses each v1
counterpart's inputs. Every file has `"protocol_version": "v2-draft"`.

| File | What it pins |
|---|---|
| `dm_pipe_001`, `dm_pipe_002` | v1 DM inputs without and with a geo-fence (20 and 23 fields) |
| `dm_pipe_003` | `\|` and `\` inside DM fields, carried verbatim |
| `dm_pipe_004` | Negative: the §I.13 geo-fence strip. `claimed_signature_hex` (dm_pipe_002's v2 signature) MUST NOT verify. |
| `post_pipe_001`, `post_pipe_002` | Post, and a post whose text ends in `\|friends` (still 9 fields) |
| `ack_pipe_001` | ACK plus `relay_key` (§2.3) |
| `stop_pipe_001` | Stop |
| `frame_json_001` | v1 frame. The JCS text equals v1's canonical text here. |
| `frame_json_002` | JCS edge cases: floats, `-0`, `/`, non-ASCII, a control character, UTF-16 key order |

Pipe vectors list the signed `fields`, `signing_bytes_hex` and the signature.
Frame vectors list `canonical_utf8` and `signing_bytes_hex`. The generator
self-checks framing round-trips and the RFC 8785 Appendix B number samples.
It also asserts that the dm_pipe_004 envelope collides with dm_pipe_002 under
v1 but not under v2.

## 5. Rollout (per `shared-vectors/VERSIONING.md`)

1. Ports implement §2 and §3 behind the version signal and pass the v2
   vectors.
2. v1 and v2 verifiers run in parallel. During that period v1 receivers keep
   enforcing the MESH_PROTOCOL.md §D rule that rejects `|` inside signed
   fields.
3. When the fleet is on v2, the v1 canonicalization vectors get
   `"deprecated_in_v2": true`, and the `v2/` files are frozen.
